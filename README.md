# DeepSeek Harness 实践指南：如何组装一个真正可用的 Agent

> 本文面向只了解 Agent、Prompt、Tool 等基础概念的读者。它不讲内部框架原理，而是帮助你理解 DeepSeek Harness（下文简称 **DSH**）能做什么、各类能力如何分工，以及怎样把它们组合成一个可直接使用的 Agent。

## 先用一句话理解 DSH

DSH 是一个**可插拔的 Agent 运行环境**：模型负责理解和决策，插件负责提供工具、规则、知识、服务、存储和界面，preset 负责把这些能力组合成一种可以直接选择的 Agent。

可以把它想成一套角色装备系统：

- 模型是“大脑”；
- Tool 是“手”；
- Prompt 是“常驻工作守则”；
- Skill 是“需要时再翻阅的操作手册”；
- Provider 是“能力供应者”；
- Consumer 是“能力使用者”；
- Preset 是“已经配好的角色、规则和整套装备”。

因此，使用 DSH 的重点不是训练模型，而是决定：Agent 能看到哪些说明、能调用哪些动作、动作背后由谁提供能力、哪些规则必须由程序保证，以及怎样把这些东西包装成可复用配置。

---

## 一、DSH 的能力地图

“插件”不等于“工具”。工具只是插件能够贡献的一种能力。一个成熟的 DSH Agent 通常由下面几类能力组合而成。

| 能力类型              | 它解决的问题                         | 常见用途                               |
| --------------------- | ------------------------------------ | -------------------------------------- |
| Tool                  | Agent 能执行什么动作                 | 查询数据、生成文件、运行程序、修改状态 |
| Skill                 | Agent 遇到某类任务时应参考什么说明   | 调研流程、写作规范、业务操作手册       |
| Prompt                | Agent 每一轮都必须遵守什么           | 角色设定、安全边界、固定工作习惯       |
| Command               | 用户如何直接执行快捷操作             | `/status`、`/remember`、管理命令       |
| Event Hook            | 如何观察或拦截执行过程               | 日志、审批、审计、结果检查             |
| Service Provider      | 谁来提供一项实际能力                 | 时间、存储、随机数、业务状态机         |
| Service Consumer      | 谁来使用这项能力                     | 将服务包装成工具、命令、API 或界面     |
| Storage/Attachment    | Agent 如何保留数据和交付文件         | 跨会话记忆、图片、报告、运行产物       |
| Code Runtime          | Agent 如何执行和验证程序             | 计算、数据处理、脚本验证               |
| Nested LLM/Agent Loop | 一个工具如何继续调用模型或运行子循环 | 自我审阅、规划—执行—纠错               |
| Web/UI                | 如何提供聊天以外的交互界面           | 状态面板、游戏界面、业务控制台         |
| Preset                | 如何把整套能力变成可选择的 Agent     | 研究助手、发布助手、主持人、审计员     |

### 1. Tool：让 Agent 真正“动手”

Tool 是模型可主动调用的函数。一个工具至少应该说明它能做什么、什么时候使用、参数怎样填写、成功会返回什么，以及失败时模型能看到什么。

例如，“查询指定城市天气”适合做成 Tool，因为它需要实时查询；“回答时保持简洁”不适合做 Tool，因为它是常驻规则，应该放进 Prompt。

一个插件可以注册一个或多个 Tool。相关操作适合放在一起，但不要把完全无关的能力塞进同一个插件，否则配置、权限和维护都会变乱。

### 2. Skill：按需加载的操作手册

Skill 是一段可由 Agent 在需要时加载的说明，适合承载标准流程、领域知识、较长步骤以及不需要每轮都占用上下文的指导。

Skill 通常不执行动作。它告诉 Agent“应该怎样做”，真正的动作仍由 Tool 完成。

### 3. Prompt：每轮都生效的工作守则

Prompt 插件向常驻上下文加入规则，例如 Agent 的角色、安全边界、不能伪造实时数据，以及完成任务后必须报告验证结果。

稳定且经常需要的规则放进 Prompt；篇幅较长、只在特定任务中需要的教程则拆成 Skill。

### 4. Command：用户直接触发的快捷入口

Command 是面向人的命令，不需要模型判断是否调用。例如：

```text
/status
/remember project = demo
/reset-session
```

确定、频繁、无需自然语言理解的操作很适合做 Command。它执行快、结果可预测，也不会因为模型误判而漏掉。

### 5. Event Hook：审计、审批和执行保护

插件可以在 Tool 执行前后介入：记录调用、识别风险、请求用户批准、拒绝未授权动作、记录结果或检查输出。

这比只在 Prompt 中写“请谨慎操作”可靠得多。Prompt 负责提醒模型，Hook 和审批负责真正建立安全边界。

```text
模型准备调用 Tool
        ↓
执行前 Hook 检查风险
        ↓
必要时请求用户批准
        ↓
执行 Tool
        ↓
执行后 Hook 记录或检查结果
```

### 6. Service：把能力与 Agent 入口分开

当一项能力会被多个工具、命令或页面复用时，不应在每个入口里重复实现。更实用的做法是：Provider 提供能力，Consumer 使用能力并将其包装成 Tool、Command、API 或 UI。

例如，一个时间 Provider 可以同时被三个 Consumer 使用：一个注册查询工具，一个每天生成报告，一个在网页上显示时钟。它们共享能力，但入口不同。

### 7. Config 与结构化输出

实用插件不应把行为全部写死。时区、语言、默认模型、最大步数、超时、存储位置和审批策略都适合做成 Config。这样同一份代码可以服务多个 preset。

Tool 输出也应尽量分成：

- **结构化值**：给程序校验、存储和继续处理；
- **可读文本**：给模型和用户理解。

例如，时间工具除了显示“现在是周六下午三点”，还可以返回：

```json
{
  "iso": "2026-08-22T15:00:00+08:00",
  "weekday": 6,
  "isWeekend": true
}
```

这样后续功能可以直接使用 `isWeekend`，无需再解析自然语言。

### 8. 生命周期：卸载时清理影响

插件可能注册工具、监听事件、启动定时器、打开资源或挂载子插件。卸载时，这些影响也应该一起撤销。

可以记住一条原则：**插件启动时增加的每一项长期影响，都应该有对应的清理方式。** 否则重新加载后容易出现工具重复、监听器叠加或旧定时器继续运行。

### 9. 持久化记忆与附件

对话历史不等于可靠的长期存储。用户偏好、项目说明和已确认的业务规则，应由插件明确保存，并区分作用域：

- 会话级：只供当前对话使用；
- 全局级：允许不同会话共享。

当 Agent 要交付图片、报告或其他文件时，应使用附件能力保存并返回稳定引用，而不是把二进制内容硬塞进文本消息。

### 10. 代码运行与嵌套模型调用

Tool 可以连接代码运行环境，让 Agent 执行计算、处理数据、运行脚本并根据真实结果修正代码。

插件也可以在一次 Tool 调用内部再次调用模型。例如，审阅工具收到草稿后，发起一次嵌套模型调用生成审阅意见，再把结果交回主 Agent。

更进一步，可以在工具内部运行小型 Agent 循环：

```text
生成方案 → 执行 → 观察错误 → 修改 → 再执行 → 完成
```

这适合目标明确、步骤有限且能被真实结果验证的任务。必须设置最大步数、超时和失败出口，避免循环失控。

### 11. Web/UI：不必把所有操作塞进聊天框

持续状态、流程按钮、图表、事件日志和复杂配置更适合可视界面。UI 通常也是 Consumer：它不重新实现业务规则，而是调用同一个 Provider。这样 Tool、Command 和网页操作的是同一份状态。

## 二、Definition、Provider 与 Consumer 的关系

### Definition：能力契约，不是运行插件

Definition 只约定服务名称、可用方法和输入输出。它类似一份插座规格，告诉实现者和使用者怎样连接；它本身不供电，因此**不应被单独安装或挂载为插件**。

### Provider：真正提供能力的插件

Provider 按照 Definition 实现功能。例如同一个随机数能力可以有正式 Provider 和测试 Provider：前者返回真实随机结果，后者固定返回结果以便复现测试。运行时通常选择其中一个。

### Consumer：使用能力的插件

Consumer 不关心 Provider 内部怎样实现，只使用 Definition 约定的方法，并把能力变成 Tool、Command、HTTP API、可视化页面或更高级的业务能力。

所以正确的运行组合是：

```text
一个 Provider + 一个或多个 Consumer
```

而不是单独挂载 Definition。这种拆法的关键价值是**可替换**：更换 Provider 时，Consumer 不需要修改。

## 三、Agent 怎么知道该使用哪个 Tool

Agent 并不会自动阅读所有插件源代码。它主要依据 Tool 名称、description、参数说明、系统 Prompt、已加载 Skill 和用户当前任务做选择。

下面这种描述信息不足：

```text
天气工具。
```

更实用的写法是：

```text
查询指定城市的实时天气和未来预报。当用户询问当前温度、降雨、空气状况或出行天气时使用；实时信息不得凭模型记忆回答。
```

它同时回答了“能做什么”和“什么时候必须使用”。

| 说明位置         | 应回答的问题                   |
| ---------------- | ------------------------------ |
| Tool description | 我能做什么，什么时候调用我？   |
| 参数 description | 每个输入应该怎样填写？         |
| Prompt           | 整个 Agent 始终遵守什么策略？  |
| Skill            | 遇到某类复杂任务时具体怎么做？ |

简单 Tool 先把 description 和参数说明写好即可。多个 Tool 容易混淆、必须按固定顺序调用、Agent 有明确业务流程，或返回结果需要固定处理时，再增加 Prompt 或 Skill。

Tool 不被调用时，依次检查：

1. 当前对话是否真的拥有该 Tool；
2. description 是否包含明确使用场景；
3. 参数是否容易理解；
4. 是否存在功能和描述高度重叠的 Tool；
5. Prompt 是否有相反要求；
6. 用户任务是否真的需要外部动作；
7. Tool 是否更新过，但当前对话仍持有旧清单。

## 四、为什么 Tool 修改或重装后仍没有更新

新增 Tool、修改参数、改变 description，甚至卸载再安装插件后，都可能继续看到旧行为。这些现象通常来自同一原因：**当前对话的工具快照与模块缓存没有同时更新。**

### 当前对话的工具快照

当前对话可用的 Tool 通常在对话创建时确定。运行中新增、删除或修改 Tool 后，旧对话未必实时获得新定义。

处理方式：**创建新对话验证。**

### 插件模块缓存

如果插件仍使用同一个模块地址，即使卸载再安装，运行环境也可能复用之前加载的代码：

```text
file:///C:/path/to/my-plugin/src/index.js
```

解决方法是在地址后增加缓存破坏参数：

```yaml
- id: my-plugin
  name: file:///C:/path/to/my-plugin/src/index.js?t=1
```

以后每次需要强制重新导入代码时递增数字：

```text
?t=1 → ?t=2 → ?t=3
```

`t` 没有业务含义，只是让模块地址发生变化，从而避开旧缓存。

### 推荐刷新流程

1. 保存源码；
2. 将模块地址中的 `?t=N` 加一；
3. 等待插件重新挂载；
4. 创建新对话；
5. 检查 Tool 名称、description 和参数；
6. 执行一次典型调用，确认实际运行的也是新代码。

可以记成一句话：**改代码时递增 `?t=N`，改 Tool 定义后新建对话。**

如果只修改可热刷新的配置，没有修改模块代码，通常不需要递增参数。Prompt、Skill、网页文件和 Tool 的刷新方式也可能不同，不要因为页面已经变化，就推断 Tool 一定更新了。

## 五、Preset 如何定制

Preset 是“一套已经配置好的 Agent 配方”。它不是单个 Prompt 或插件列表，而是角色说明、能力组合、配置与状态隔离的整体。

一个典型 preset 至少包含：

```text
my-preset/
├── preset.yml          # 名称、描述等展示信息
└── agent.cordis.yml    # 插件组合与配置
```

复杂 preset 还可以附带专用插件：

```text
my-preset/
├── preset.yml
├── agent.cordis.yml
└── plugins/
    ├── runtime/        # Provider：业务规则和状态
    ├── tools/          # Consumer：模型工具和提示
    └── web/            # Consumer：可选界面
```

### 第一步：用一句话定义角色

例如：

```text
这是一个项目发布助手，负责检查版本、运行测试和生成变更摘要，但真正发布前必须获得用户确认。
```

### 第二步：把需求分到正确的能力类型

| 需求                         | 合适的能力            |
| ---------------------------- | --------------------- |
| 检查版本、运行测试、执行发布 | Tool                  |
| 发布流程说明                 | Skill                 |
| 发布前必须总结影响           | Prompt                |
| 真正发布前要求确认           | Event Hook + Approval |
| 记住项目发布偏好             | Storage               |
| 展示测试和发布状态           | Web/UI                |
| 封装项目操作能力             | Provider              |
| 将能力包装成 Tool 和页面     | Consumer              |

### 第三步：组合 Provider 与 Consumer

```yaml
- id: project-runtime
  name: file:///C:/path/to/my-preset/plugins/runtime/src/index.js?t=1

- id: project-tools
  name: file:///C:/path/to/my-preset/plugins/tools/src/index.js?t=1
```

不要挂载仅声明契约的 Definition。运行组合应包含实际 Provider 和所需 Consumer。

### 第四步：配置差异，不要复制代码

如果两个 preset 只是模型、最大步数、语言、时区、审批策略、存储路径或默认参数不同，应为插件提供 Config，再由不同 preset 传入不同值。

### 第五步：隔离有状态的能力

如果 Provider 保存游戏进度、工作流进度或临时数据，就要避免不同会话共用同一份状态。可以记住：**有会话私有状态的 Provider，与依赖它的 Consumer 应作为一组隔离。**

同时区分：

- 全局状态：多个会话允许共享；
- 会话状态：只属于当前 Agent；
- 私有角色状态：多 Agent 场景下只允许指定角色看到。

Prompt 只能告诉模型“不要偷看”，真正的可见性隔离必须由 Provider 在返回数据时保证。

### 第六步：验证完整流程

一个 preset 至少要验证：

1. 能否被发现和选择；
2. 能否成功创建新对话；
3. 所需 Tool 是否可见；
4. Tool 的 description 和参数是否正确；
5. 典型任务能否完整跑通；
6. 危险动作是否真正触发审批；
7. 两个会话的私有状态是否隔离；
8. 修改插件后递增 `?t=N` 并新建对话，能否看到新版本。

## 六、DSH 与其他 Agent 方案的区别

### 与 DeepAgents 的区别

| 对比点   | DSH                                   | DeepAgents                        |
| -------- | ------------------------------------- | --------------------------------- |
| 主要定位 | 可长期运行和扩展的 Agent 宿主         | 用代码构建任务型 Agent 的开发框架 |
| 常见入口 | Profile、插件、Preset、会话           | 创建 Agent、配置工具和执行流程    |
| 定制思路 | 给宿主挂载并组合能力                  | 在应用代码里定义一个 Agent        |
| 更适合   | 个人 Agent 环境、可切换角色、插件生态 | 在应用中实现特定 Agent            |

简单说：**DeepAgents 更像开发一个 Agent 应用，DSH 更像组装并运行一套 Agent 工作台。**

### 与 Codex 的区别

| 对比点       | DSH                                   | Codex                              |
| ------------ | ------------------------------------- | ---------------------------------- |
| 默认目标     | 组装不同用途的 Agent                  | 在真实代码仓库中完成编码任务       |
| 主要扩展方式 | 插件、Provider/Consumer、Preset       | 工具、Skills、项目指令和连接器     |
| 默认体验     | 自己决定安装和组合哪些能力            | 编码、修改、测试和审查工作流较完整 |
| 适用范围     | 助手、业务工具、游戏、多 Agent 实验等 | 软件开发与仓库协作                 |

想直接完成代码修改和测试，Codex 更接近开箱即用的编码 Agent；想决定一个 Agent 的角色、能力组成和运行方式，DSH 提供更通用的组装空间。

一句话概括：**Codex 重点是把编码任务做好，DSH 重点是让你决定 Agent 到底是什么。**

### 与 PI Agent 的区别

> 这里的 PI Agent 指轻量、可编程、偏编码工作流的 PI Agent，而不是其他同名产品。

| 对比点   | DSH                                   | PI Agent                  |
| -------- | ------------------------------------- | ------------------------- |
| 风格     | 插件平台与 Agent 宿主                 | 轻量 Agent 核心与编码助手 |
| 能力组织 | 插件、服务、Provider/Consumer、Preset | 工具、扩展和消息循环      |
| 学习重点 | 挂载、组合、隔离和复用能力            | 控制 Agent 循环和交互体验 |
| 更适合   | 多种 Agent 配方和长期插件化扩展       | 从简洁 Agent 出发快速改造 |

可以把它们理解成两条路线：**PI Agent 更像拿一个轻巧的 Agent 核心来改，DSH 更像在插件底座上拼出不同 Agent。**

## 七、推荐的上手顺序

1. 注册一个最小 Tool，确认模型能够选择并调用；
2. 分别添加 Prompt 和 Skill，理解常驻规则与按需说明；
3. 添加 Command，体验用户直接触发的入口；
4. 将一项能力拆成 Provider 和 Consumer；
5. 为插件增加 Config 和结构化输出；
6. 添加执行前审批和执行后审计；
7. 增加持久化记忆或附件交付；
8. 接入代码运行或一次嵌套模型调用；
9. 将相关插件组合成一个 preset；
10. 最后尝试带私有状态隔离的多 Agent 场景和可视界面。

遇到“代码明明改了却没生效”，优先检查模块地址是否递增了 `?t=N`，以及是否创建了拥有新 Tool 快照的对话。

掌握这套分工后，DSH 就不再是一堆抽象概念，而是一套直观的组装方法：**用 Prompt 定角色，用 Skill 教流程，用 Tool 做动作，用 Provider 提能力，用 Consumer 接入口，用 Hook 守边界，最后用 Preset 把整套 Agent 交付出去。**
